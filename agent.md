```rust
1.2. Основные структуры данных

// analyzer/mod.rs
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ProcessInfo {
    pub pid: u32,
    pub name: String,
    pub path: Option<String>,      // полный путь к исполняемому файлу
    pub parent_pid: Option<u32>,
    pub cpu_usage: f32,
    pub mem_usage: u64,            // байт
    pub is_suspended: bool,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ProcessGroup {
    pub id: String,                // уникальный идентификатор (например, хэш пути установки)
    pub name: String,              // отображаемое имя (Mozilla Firefox)
    pub processes: Vec<ProcessInfo>,
    pub load_score: f64,
    pub status: GroupStatus,       // Active, Sleeping, Ignored
    pub auto_start_entries: Vec<AutoStartEntry>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum GroupStatus {
    Active,
    Sleeping,
    Ignored,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum AutoStartEntry {
    Registry { key: String, value: String },
    StartupFolder { path: String },
    ScheduledTask { name: String },
}
```
2. Этап 1: Сканирование и инвентаризация (Rust)
2.1. Чтение реестра (автозагрузка и uninstall)
Крейт: winreg 0.50.

Задачи:

Открыть ключи HKCU\Software\Microsoft\Windows\CurrentVersion\Run, HKLM\...\Run, RunOnce.

Прочитать значения (имя программы и путь к исполняемому файлу).

Для группировки также прочитать раздел HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall и HKCU\...\Uninstall, чтобы получить DisplayName, InstallLocation.

Пример:

```rust
use winreg::RegKey;
use winreg::enums::*;

fn read_run_entries() -> Vec<AutoStartEntry> {
    let hklm = RegKey::predef(HKEY_LOCAL_MACHINE);
    let run_key = hklm.open_subkey(r"SOFTWARE\Microsoft\Windows\CurrentVersion\Run")?;
    for (name, value) in run_key.enum_values() {
        // name - имя записи, value - путь к исполняемому файлу
    }
    // аналогично HKCU
}
```
2.2. Папки автозагрузки
Использовать std::fs для обхода папок:

C:\ProgramData\Microsoft\Windows\Start Menu\Programs\StartUp

%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup

Получить список файлов .lnk и .exe, извлечь целевой путь через COM (или через std::fs::read_link для симлинков, но ярлыки сложнее – придется использовать ShellLink из windows-rs).

2.3. Планировщик задач
Крейты: taskschedule (обертка) или использовать windows-rs с COM-интерфейсом ITaskScheduler.

Альтернатива: запускать schtasks /query /fo csv /v и парсить вывод CSV (проще, но медленнее и зависит от локали).

Рекомендуется использовать windows-rs для надежности.

Задача: получить список всех задач, их состояние (включена/отключена), путь к исполняемому файлу.

2.4. Службы Windows
Крейт: windows_service или windows-rs с EnumServicesStatusEx.

Получить имя службы, отображаемое имя, состояние, путь к исполняемому файлу.

2.5. Активные процессы
Крейт: sysinfo 0.30.

Получить список всех процессов: PID, имя, родительский PID, загрузка CPU (в процентах), использование памяти.

Записать эти данные в структуру ProcessInfo.

3. Этап 2: Группировка и расчет «Точек нагрузки»
3.1. Алгоритм группировки
Шаг 1: Собрать все процессы, службы, задачи автозагрузки и записи реестра в единый пул «сущностей».

Шаг 2: Сгруппировать по общему пути установки:

Для каждого исполняемого файла извлечь родительскую папку (например, C:\Program Files\Mozilla Firefox).

Если несколько сущностей имеют общий корневой путь (глубже Program Files или Program Files (x86)), объединить их в одну группу.

Шаг 3: Если путь не совпадает, проверить общего родительского процесса (через parent_pid). Например, дочерние процессы обновления принадлежат родительскому Firefox.

Шаг 4: Если всё еще не удалось, искать по общему ключу Uninstall – сравнивать InstallLocation и DisplayName (если совпадают на 80%).

Шаг 5: Если группа не найдена, создать группу для каждого отдельного процесса (одиночный элемент).

Результат: список ProcessGroup.

3.2. Расчет балла нагрузки (Load Score)
Для каждой группы вычисляем:

cpu_avg – средняя загрузка CPU по всем процессам (в процентах)

mem_total – суммарное потребление памяти (в МБ)

process_count – количество процессов в группе

auto_start_count – количество точек автозапуска (записи реестра + папки + задачи)

Формула:
```rust
let load_score = (cpu_avg * 0.4) + ((mem_total / 100.0) * 0.3) + ((process_count * 5.0) * 0.2) + ((auto_start_count * 10.0) * 0.1);
```
Коэффициенты подбираются эмпирически. Итоговый балл можно масштабировать до 100.

3.3. Определение «Slowdown severity»
На основе балла:

Красный (> 60) – высокая нагрузка

Желтый (30–60) – средняя

Зеленый (< 30) – низкая

4. Этап 3: Пользовательский интерфейс (UI)
4.1. Выбор фреймворка
Рекомендация: egui (иммедиатный режим, простой, быстрое прототипирование).

Альтернативы: slint (декларативный, нативный вид), tauri (если нужен веб-интерфейс, но он тяжелее).

В примере используем egui с бэкендом eframe.

4.2. Сценарий запуска и жизненный цикл окна
После запуска приложение создает фоновый мониторинг и иконку в системном трее. Главное окно создается скрытым и не показывается автоматически.

Открыть главное окно можно двумя способами:

- выбрать пункт «Открыть» в меню системного трея;
- дважды щелкнуть по иконке приложения в трее.

При открытии окно становится видимым, восстанавливается из свернутого состояния и получает фокус. Повторная команда «Открыть» не создает второе окно.

Нажатие системной кнопки закрытия главного окна не завершает приложение, а скрывает его обратно в трей. Полное завершение выполняется только пунктом «Выйти» в меню трея. Перед завершением приложение останавливает мониторинг, сохраняет состояние и удаляет иконку из трея.

4.3. Компоненты управления UI и треем
Структура `ProgramDeactivatorApp` отвечает только за состояние и отрисовку главного окна.

Свойства:

- `state: Arc<Mutex<AppState>>` — общее состояние групп и фонового мониторинга;
- `window_controller: WindowController` — управление видимостью окна;
- `tray_event_rx: Receiver<TrayAction>` — прием команд из системного трея;
- `shutdown_requested: bool` — признак корректного завершения приложения.

Методы:

- `new(...) -> Self` — создает UI со скрытым главным окном и подключает канал событий трея;
- `update(&mut self, ctx: &egui::Context, frame: &mut eframe::Frame)` — обрабатывает события трея и рисует главное меню;
- `handle_tray_action(&mut self, action: TrayAction)` — выполняет открытие окна или полное завершение;
- `request_hide(&mut self)` — перехватывает закрытие главного окна и скрывает его в трей;
- `shutdown(&mut self)` — сохраняет состояние и корректно останавливает фоновые задачи.

Структура `TrayController` отвечает только за системный трей.

Свойства:

- `icon` — созданная иконка трея;
- `open_menu_id` — идентификатор пункта «Открыть»;
- `exit_menu_id` — идентификатор пункта «Выйти»;
- `action_tx: Sender<TrayAction>` — канал передачи действий в UI.

Методы:

- `new(action_tx: Sender<TrayAction>) -> Result<Self>` — загружает иконку и создает меню трея;
- `handle_menu_event(&self, event)` — преобразует выбор пункта меню в `TrayAction`;
- `handle_icon_event(&self, event)` — открывает окно по двойному щелчку;
- `set_tooltip(&self, text: &str)` — обновляет подсказку иконки;
- `shutdown(self)` — удаляет иконку перед завершением процесса.

`WindowController` отвечает только за состояние главного окна.

Методы:

- `show(&mut self, ctx: &egui::Context)` — показывает, восстанавливает и фокусирует существующее окно;
- `hide(&mut self, ctx: &egui::Context)` — скрывает окно без остановки приложения;
- `is_visible(&self) -> bool` — возвращает текущее состояние видимости.

Перечисление `TrayAction` содержит команды `OpenMainWindow` и `ExitApplication`. События трея передаются в UI через `std::sync::mpsc`, чтобы обработчики трея не изменяли `egui`-состояние напрямую.

4.4. Основные экраны
Главная таблица: колонки "Имя группы", "Балл нагрузки", "Статус" (Active/Sleeping/Ignored), кнопка "Усыпить/Разбудить".

Детали: по двойному клику открывается окно со списком всех процессов, служб, задач автозагрузки в группе.

Панель управления: кнопка "Запустить сканирование" (обновить данные), "Сохранить состояние".

4.5. Цветовая индикация
Состояние Sleeping – серый фон, Active – зеленый, Ignored – синий.

Балл нагрузки – цвет текста/фона: красный/желтый/зеленый.

5. Этап 4: Деактивация («Усыпление»)
5.1. Приостановка процессов (Suspend)
Используем windows-rs с функцией NtSuspendProcess из ntdll.dll.

Для каждого процесса в группе (кроме критических системных) вызываем NtSuspendProcess(handle).

Необходимо получить хендл процесса с правами PROCESS_SUSPEND_RESUME.

Пример:

```rust

use windows::Win32::System::Threading::{NtSuspendProcess, NtResumeProcess};
use windows::Win32::Foundation::HANDLE;
use windows::Win32::System::ProcessStatus::OpenProcess;
use windows::Win32::System::Threading::PROCESS_SUSPEND_RESUME;

fn suspend_process(pid: u32) -> Result<()> {
    let handle = unsafe { OpenProcess(PROCESS_SUSPEND_RESUME, false, pid)? };
    unsafe { NtSuspendProcess(handle) }?;
    Ok(())
}

```

5.2. Отключение автозагрузки
Реестр: удалить (или переименовать) записи Run, RunOnce, принадлежащие группе (сохраняя их в состоянии для восстановления).

Папки Startup: переместить ярлыки в подпапку Disabled внутри той же папки.

Планировщик: отключить задачу через schtasks /change /disable /tn "TaskName" или через windows-rs с ITaskScheduler::put_Enabled(false).

Службы: изменить тип запуска на Disabled (через ChangeServiceConfig), но быть осторожным – службы могут быть системными.

5.3. Сохранение состояния
Сериализовать список ProcessGroup с пометкой status = Sleeping в JSON-файл в %APPDATA%\ProgramDeactivator\state.json.

При следующем запуске приложение читает этот файл и восстанавливает состояние.

6. Этап 5: Самоактивация («Пробуждение»)
6.1. Мониторинг запуска новых процессов
Вариант А (рекомендованный): Использовать WMI-события через крейт wmi.

Подписаться на __InstanceCreationEvent для класса Win32_Process.

При получении события – проверить, принадлежит ли новый процесс какой-либо «спящей» группе (по имени исполняемого файла или полному пути).

Вариант Б (проще): Периодический опрос через sysinfo каждые 1–2 секунды в фоновом потоке.

Сравнивать текущий список PID с предыдущим; если появился новый PID, проверить его имя по состоянию.

Реализация выбора: для мгновенной реакции лучше WMI, но он требует прав администратора и дополнительной настройки. В MVP можно использовать опрос.

6.2. Логика пробуждения
Если обнаружен запуск процесса, входящего в «спящую» группу:

Вызвать NtResumeProcess для всех процессов этой группы (которые были приостановлены).

Восстановить автозагрузку (опционально – можно оставить отключенной, чтобы не мешать, но многие пользователи ожидают, что программа снова будет запускаться автоматически).

Обновить статус группы на Active и сохранить состояние.

7. Этап 6: Повторная деактивация («Засыпание»)
7.1. Мониторинг завершения процессов
Аналогично, через WMI (__InstanceDeletionEvent для Win32_Process) или через опрос.

Отслеживать, когда процессы из активной группы завершаются.

7.2. Условие перехода в сон
Если все процессы группы завершены (т.е. ни один процесс из группы не активен), то:

Снова применить деактивацию (приостановка оставшихся, отключение автозапуска).

Обновить статус на Sleeping.

Важно: Если пользователь вручную запустил процесс, а потом закрыл его – группа должна снова «уснуть».

UI работает в основном потоке (например, с eframe).

Использовать Arc<Mutex<State>> для безопасного доступа к общему состоянию из разных потоков.

- иконка трея удаляется после штатного завершения;
- ошибка загрузки иконки или создания трея отображается в журнале и приводит к показу главного окна, чтобы приложение не осталось недоступным.
